## 已确认的功能问题

### R1 · P1：换房后，相同预设可能不再发布

位置：[PublishShareStateIfNeeded](C:/Users/Administrator/Desktop/MOD/PEAK/MOD开发/WhereIsThing/WhereIsThing/WhereIsThingPlugin.cs:1798)，关联 `UpdateRoomState` 第 1753–1766 行、`OnMasterClientSwitched` 第 1972–1977 行。

去重仅比较 payload 与由 payload 算出的 hash，缓存没有带上房间、发布者和共享模式。换房/成为房主仅设置 dirty，没有使旧发布缓存失效。

- 触发：同一进程先在房间 A 作为房主发布，再进入房间 B 作为房主，预设内容不变。
- 隔离结果：A 发布成功；B 的发布调用为 0，dirty 却被清除。新房间没有获得 WIT 属性，客机只能使用回退预设。
- 同一根因：`BuiltInOnly` 与 `Off` 都序列化为空 payload，只切模式也会被当成“已发布”，房间 `WIT.ShareMode` 保留旧值。当前两者均走回退，因此此子项的用户影响小于跨房漏发布。
- 建议：以当前房间会话、房主 actor、mode、protocol 和 payload 共同决定发布身份；离房/换房/房主变化使缓存失效。处理 `SetCustomProperties` 未成功提交时的重试，不要直接记成已发布。
- 验证等级：真实方法体 + Photon 房间替身；未进行真实联机。

### R2 · P1：物品目录首次解析后，共享预设可能仍是空目标或旧目标

位置：[TryLoadCatalog](C:/Users/Administrator/Desktop/MOD/PEAK/MOD开发/WhereIsThing/WhereIsThing/WhereIsThingPlugin.cs:1071)，第 1071–1076 行。

房主进入房间的 `UpdateRoomState` 可以先发布预设；目录要到打开选择窗口、开始扫描等路径才加载。新建的部分内置预设此时尚无物品 ID。`TryLoadCatalog` 后续会做真实身份/放置物迁移、解析内置目标和保存，但没有标记共享状态需要重新发布。

- 隔离结果：先发布未解析的 Survival，加载含药用根茎的目录后，本地已包含测试 ID 501，房间中的 Survival 物品列表仍为空。501 仅为测试 ID，不是游戏资产身份记录。
- 影响：本地看起来正常，客机收到的预设不完整；直到另一次编辑或其他事件触发发布才恢复。仅在目录解析/迁移实际改变待共享内容时发生，不是每次启动必现。
- 建议：目录解析和迁移完成后，比较共享内容修订号/序列化结果，变化时标 dirty，并确保首次有效目录就绪后重新发布。
- 验证等级：真实主流程与目录/预设 helper + 测试物品库；配置保存等非关键依赖为替身，并核对真实保存函数没有补做 MarkShareDirty。

### R3 · P2：无关房间属性会延长定时扫描，并重建客机窗口

位置：[OnRoomPropertiesUpdate](C:/Users/Administrator/Desktop/MOD/PEAK/MOD开发/WhereIsThing/WhereIsThing/WhereIsThingPlugin.cs:1959)，关联 [计时重置](C:/Users/Administrator/Desktop/MOD/PEAK/MOD开发/WhereIsThing/WhereIsThing/WhereIsThingPlugin.cs:1441)。

回调不检查变更是否包含 WIT 属性；任何房间属性变化都调用 `RefreshEffectivePresetState(true)`，并在预设窗口打开时再次 Open。关闭客机限制、正在使用本地预设的客机也会执行这段逻辑。

- 隔离结果：原截止时刻为 108；在时刻 105 收到 `UnrelatedGameKey`，截止被改为 113，窗口刷新也被调用。
- 实际窗口代码：Open 第 265 行先关闭重命名框，第 268 行重建行；RebuildRows 第 324–326 行销毁旧行。因此无关属性会打断开放编辑客机的重命名输入，并制造额外 UI 分配。
- 建议：先过滤协议相关 key，再比较实际共享状态是否变化；未使用共享预设时不要重建本地编辑器。分开“刷新显示内容”和“用户重新触发计时”，避免每次状态同步都续时。
- 验证等级：截止时间与窗口调用已隔离重现；关闭重命名/销毁行的效果来自真实窗口静态控制流。

### R4 · P2：从 ModConfig 把常驻改成定时，已有标签可能一直不消失

位置：[RefreshEffectivePresetState](C:/Users/Administrator/Desktop/MOD/PEAK/MOD开发/WhereIsThing/WhereIsThing/WhereIsThingPlugin.cs:1431)，关联主循环第 305–315 行。

自己的预设窗口会走刷新并重设计时；ModConfig 直接改配置没有对应 SettingChanged 或扫描模式观察。周期刷新只更新 `_effectiveScanMode`，不会重新计算 `_hideAt`。

- 隔离结果：常驻状态的截止时间为正无穷，外部配置切成定时后，模式已变成 Timed，截止时间仍为正无穷。
- 影响：本轮已在显示的标签无法按新定时模式到期，重新扫描等事件才会校正。
- 建议：统一配置变更入口，明确模式/时长切换对当前扫描的计时规则；对外部配置与内部 UI 使用同一路径。
- 验证等级：真实状态刷新方法 + 配置替身；ModConfig 控件交互未实机验证。

## 边界与遗漏：不要混同已复现的正常游戏故障

1. **通用 additionalFilter 的生命周期不完整。** 主插件第 832 行只在发现时检查附加条件，第 842–843 行旧标签有效性不包含该条件；现有 seen 集合也没有扫尾消费端。隔离条件从 true 变 false、对象保持 active 时旧标签仍有效。但目前实际调用只用 HasRunSetting 检查父组件/枚举类型；PEAK 3.1.0 的 DisableBasedOnRunSettings 关闭危险时直接 SetActive(false)，现有 active 检查会清标签。因此只列为父层级/组件改变或未来可变过滤器的维护缺口，不能声称正常关闭危险就必然残留。
2. **打开选择窗口会暂停标签维护。** 主插件第 268–285 行提前返回，Enabled、到期清理、位置/有效性更新均在后面；标签类没有独立 MonoBehaviour 更新。若窗口中仍显示标签，它们会停留在旧位置，已摘目标/到期扫描要等窗口关闭后才清理。控制流已确认，是否保留“菜单中暂停维护”行为需按交互目标决定，视觉表现未实机验证。
3. **重命名 Escape 可能连带关闭整个预设窗口。** Picker.Tick 第 277–279 行关重命名框，主 Update 第 281–283 行又响应同一帧 Escape 关预设窗口；如期望逐层退出，应消费按键。静态确认，未实机操作。
4. **目录就绪与晚初始化。** TryLoadCatalog 只看目录非空；若 ItemDatabase 已存在但物品表暂空，仍可能因场景/箱子条目而永久缓存“不完整目录”。实际游戏初始化顺序未重现。晚分类超过 2.1 秒后不再重试，也需验证慢联机初始化/绳索晚锚定是否需要另一个触发点。
5. **相机缓存条件偏窄。** 主插件第 733 行仅判断缓存相机不存在或 GO 非激活，没有检查 camera.enabled/主相机替换；场景加载已有清缓存。需实机验证死亡观战等同场景相机切换，不能仅凭此判定现有观战必坏。

## 本轮未发现需要撤销的近期设计

- 客机限制默认 true，false 允许本地预设；代码与“本地偏好、不是房主强制规则”的说明一致。
- 晚安莓仍为一个选择入口，内部 FakeItem 与 Item 两条发现路径；未摘标果实，采摘/隐藏/更换后撤旧标签的 helper 回归通过。无需为了统一入口把两种载体强行并成同一实体。
