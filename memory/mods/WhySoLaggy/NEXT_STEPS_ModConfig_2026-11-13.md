# WhySoLaggy ModConfig 下一步方案调研

日期：2026-11-13。用户要求调研下一步如何做。本轮只读正式代码，在 .build 内编写并执行方案实验，更新 memory；没有修改生产源码、配置、安装 DLL、版本或发行文件。

## 推荐路线

先修 PatchProfiler 的方法目标规范化、重复挂钩和补丁生命周期，再用当前完整 profile 验收。修复首先落在 WhySoLaggy 内；不要求降级游戏/ModConfig，不移除语言功能，不以修改 ShootZombies 或全局 Harmony 作为前置条件。

选择依据：本轮针对三种策略进行真实 Harmony 包装调用，目标规范化和绑定计时回调均通过测试；目前没有证据要求直接引入动态代码生成。采用改动较少、能保留计时的规范化方案作为首选。无 __originalMethod 的绑定回调保留为后备，不能把上一轮泛泛建议自动当成必须重写。

## 方案比较与本轮验证

实验文件：.build/whysolaggy-modconfig-3.1.0-20261113/history-probe/FixStrategyProbe.cs。
结果：同目录 strategy-results.txt。使用当前 0Harmony 2.9.0.0 和 MonoMod，独立 .NET Framework 进程，无游戏程序集。

| 方案 | 实验结果 | 取舍 |
| --- | --- | --- |
| 按实际闭合父类声明目标只加一次计时 | 4/4 组合通过 | 首选；保留现有计时链，改动较小 |
| 规范化目标并生成带固定 id 的计时回调，不请求 __originalMethod | 4/4 组合通过 | 后备；还需动态程序集/回调缓存、Mono 及泛型共享验证 |
| 跳过风险方法的计时 | 4/4 组合通过，但计时次数为 0 | 仅故障降级，不能称为保留了全部分析能力 |

每种策略都覆盖 int/string 泛型实参、继承目标先挂/声明目标先挂。每个组合包含：两个本地化 owner；加计时；之后再从继承目标加第三个本地化补丁；关闭计时；重新启用/停用三轮。成功条件为名称结果保持、后续翻译仍在、每次调用恰好记录一次、关闭时没有计时回调。

12/12 方案实验达到各自预期。必须与前一轮 history-probe/results.txt 区分：前一轮故障基线是 6 个成功/6 个预期泛型异常。未测 Unity/Mono 完整 profile、真实游戏 UI、所有方法类型或性能；本轮不能宣称生产修复完成。

## 第一阶段：修核心计时入口（P0）

主要文件：Helpers/PatchProfiler.cs；可提取小型 ProfilerTargetResolver 以独立测试。保留原 MethodKey 的兼容输出/忽略格式。

1. 扫描已补丁方法后，先将继承 MethodInfo 解析回实际 DeclaringType 上的声明方法。不得通过 GetBaseDefinition 无条件退到最老父类，那会改变真正重写的方法。必须保持闭合类型参数、泛型方法实参、构造函数和重载身份。
2. 当前 Harmony 的 AccessTools.GetDeclaredMember 按 MetadataToken 找成员可作基础，但其实现不显式恢复已构造泛型方法实参，不能原样套用便认为所有泛型均正确。解析后校验模块、token、声明类型和方法泛型参数；未知或不支持的形态记录跳过原因。
3. 将同一实际目标的多个反射入口合并，只挂一次。内部身份应包含 module/token/闭合声明类型/方法实参，不用仅含类型名和方法名的日志字符串代替身份。合并所有原入口的外部 owners，保留现有忽略格式。
4. 不修改其他 owner 的补丁。当前插件本地化已使用声明方法，全球扫描仍必须容忍第三方留下的继承入口。
5. 删除 TimingPrefix 未使用的 __originalMethod 参数；首选方案允许规范化后的 Postfix 暂时保留该参数。若 Mono 实机仍无法安全注入，再切换已验证的绑定 id 回调，避免一开始扩大实现。
6. 初始化时缓存目标名称和 owners；不要每次采样都构造方法签名字符串。缓存查找失败应安全跳过并限频报告，不让诊断异常传播进业务方法。
7. 添加明确计数：发现入口、规范化唯一目标、重复合并、不支持跳过、安装失败。hook 成功不能等同方法调用成功。失败时清除本次半安装的计时回调，不能清其他 MOD 补丁。

开泛型/抽象/无方法体/异常反射目标需明确降级；对支持的闭合泛型保留计时，不能未经说明全面排除泛型。普通方法的原始异常应照常传播，不以宽泛 finalizer 吞掉业务错误。

## 第二阶段：可安全关闭与恢复（P1，建议同次完成）

主要文件：WhySoLaggyPlugin.cs 与 PatchProfiler.cs。

- 使用专属 Harmony id，例如 com.wuyachiyu.WhySoLaggy.PatchProfiler。当前其他功能仍使用 PluginGuid；二者不可混用。
- 统计 owner 时显式排除自有 root id 与计时 id，不能让计时器把自己的本地化当作外部插件，也不要模糊匹配不相关 id。
- 关闭 EnablePatchProfiling：先使记录回调失效，再仅撤销专属计时补丁；确认撤销后重置统计。不得对共用 _harmony 调 UnpatchSelf，否则会撤掉本地化/RPC 等功能。
- 设置事件只记录期望状态，在 Unity 主线程的 Update/排队任务处理挂钩/撤销，避免 UI 回调或配置文件线程内重写当前正在执行的方法。启动延迟 5 秒期间的开关也需一致。
- 连续开关幂等：无重复补丁、无残留计数、无重复事件订阅。失败时保留可诊断状态和清理句柄，不能声称已停用但旧回调仍在。
- Shutdown 顺序：取消事件/待执行任务，关闭计时，撤销计时补丁，再清状态；其余模块按各自生命周期清理。

本轮不建议顺带重写所有配置热更新。优先使 EnablePatchProfiling 真正可开关；IgnorePatchMethods 可定义在下次重新启用/重启生效，并明确文案。其他配置逐项列为后续工作，不能笼统宣传全部即时生效。

## 安全记录与性能边界

本次快照中 PatchProfiler 还挂到 ExitGames.Client.Photon.SocketUdp.ReceiveLoop。现有 _timings/_frameTimers 等普通 Dictionary 没有线程保护，不能假设全局被补丁方法全在 Unity 主线程。

实施时至少明确并验证记录与报表/清理的并发策略：可采用短锁收集/快照或每目标原子计数/队列，禁止跨原方法执行持锁；记录内不调用 Unity API，也不在持锁时做 IO。此处属于防止诊断代码影响业务的必要边界，不应未经验证承诺降低开销或引入复杂性能重构。

开关运行中的回调需要处理“开始后停用、停用后回调返回”的情形，可用会话 generation 丢弃旧记录。原方法抛错、重入与并发调用都要保证计时状态不会串用。性能基准应比较同场景开启/关闭数据，不能拿隔离程序运行时间代替 FPS 结论。

## 第三阶段：测试、语言与部署

### 自动验证

- 正式回归必须调用真实 PatchProfiler，不能只测试目标查找工具，也不能只复用本轮简化实验回调。
- 覆盖继承/声明两入口、挂钩顺序、第三方后续重挂、单次计数、多 owner 汇总及忽略规则。
- 覆盖值类型/引用类型闭合泛型、构造泛型方法、普通/静态/重载/重写方法、递归和原方法异常。
- 覆盖开关三轮、初始化延迟中切换、卸载重载、局部安装失败，以及原有本地化/RPC 补丁不被误撤。
- 增加后台线程记录与主线程快照/Shutdown 并发测试，避免字典竞争异常。
- 处理 CoreBehaviorTests.cs 写死 2.4.b 的反编译路径：明确传入当前 3.1.0 基线或测试配置，不删除/静默跳过断言来获得“全绿”。
- 原有测试一起跑，输出结果与本轮隔离实验分开记录。计时和独立 id 改动若影响其他测试应更新真实语义，不能只改断言迎合实现。
