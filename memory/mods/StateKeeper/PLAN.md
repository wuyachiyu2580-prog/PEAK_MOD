## 前期调研结论归档

以下内容来自此前对 StateKeeper、PlayersInfo、PEAK 反编译代码、`LengSword-ClimbInfoTracker`、WhereIsThing、现有 GZip 局数据和 PEAK-MAP 网站源码的调研，属于本计划的设计依据。

### 一局结束的可靠基准

- 使用 PEAK 的非空 `RunManager.RunId` 绑定一局；空值只等待，不创建新局。
- 正式结束以 `Character.RPCEndGame()` 并触发 `GlobalEvents.TriggerRunEnded()` 为准。
- 同局触发 `TriggerSomeoneWonRun` 则为 Victory；只有正式结束而没有胜利事件则为失败。
- 单个玩家死亡、倒地、复活、传送、力竭、主动离开或断线都不能提前结束一局。
- 游戏崩溃、主动离开和断线保留为未完成语义；新 RunId 出现时，旧活动记录标记为 `Aborted`，不能自动和新局合并。
- 活动局使用 `active-run.json`，约每 5 秒落盘；重连后只有相同 RunId 才继续写入。

### 当前采集与样本基线

- 核心数据为所有玩家体力/额外体力/最大体力/异常状态、冲刺/攀爬/绳索/藤蔓/滑翔/力竭/死亡/倒地等状态、本机到队友距离和玩家两两距离。
- 物品数据包含主手、临时槽、背包栏位、物品 ID/名称/熟度/GUID/剩余使用次数/耐久/燃料等；地面全部场景物品不扫描。
- 事件区分 `LocalAuthoritative` 和 `RemoteObserved`；远端观察值不能伪装成本机权威数据。
- 体力和距离目标 5Hz，库存目标 2Hz；体力即时事件默认只记录绝对变化量大于或等于 `0.01` 的变化，5Hz 原始曲线不受影响。
- 已有局数据证明 GZip 碎块可用，但原始 JSON 可能达到约 88 MiB；体力小变化事件曾造成事件量膨胀，因此需要阈值、紧凑模型和后台写盘。
- 实机数据出现过少量 `RunManager.TimeSinceRunStarted` 倒退，以及短时 9-10 个角色对象；后续分析必须保留数据质量警告，不能直接静默排序或假设角色数恒定。

### 未来可分析的信息与推荐表现形式

基础分析算法先按以下规则设计；综合评分、最佳队友和复杂战术评级暂不实现：

| 数据关系 | 推荐表现形式 | 目的 |
| --- | --- | --- |
| 单局结果、时长、人数、结束原因、数据质量 | 概览卡片 + 状态标签 | 快速判断一局是否完整、胜利或中断 |
| 体力、状态、死亡/倒地、关键事件随时间变化 | 多玩家同步时间线 | 查看关键阶段、体力消耗和状态转折 |
| 玩家与玩家距离 | 距离热力图、分段趋势或关系图 | 观察队伍是否分散、集合和救援距离 |
| 物品栏、耐久、燃料、使用次数变化 | 物品流水/使用统计表 | 判断资源消耗、补给和物品使用时机 |
| 玩家状态与物品事件叠加 | 可筛选事件时间线 | 回看特定事件前后的资源和状态变化 |
| 多局相同字段 | 局间对比表和趋势图 | 只在样本量足够后做稳定比较 |

不提前承诺“综合玩家评分”“最佳队友”或复杂“战术评级”。这些结论需要足够样本、明确指标、异常数据处理和用户认可，先保留原始数据与透明的基础统计。

### 对其他玩家和联机性能的影响

- 采集以本机只读观察为主，不修改 PlayersInfo，不发送新的 Photon RPC，不广播房间统计，也不改变其他玩家状态。
- 主要成本是本机 Unity 侧采样、对象读取、少量指纹比较和后台 I/O；其他玩家不会因为 StateKeeper 收集而额外收到网络消息。
- 8 人、约 2 小时房间按固定 5Hz 采集设计，关键性能风险是主线程序列化/压缩、库存扫描、GC、结算瞬间和慢盘，而不是网络带宽。
- 合并、分析、匿名导出和上传都不能在 Unity 主线程构建完整大字符串；面板默认只读索引，打开详情时按需加载单局。
- 后续实机验收需要用 WhySoLaggy 对 StateKeeper、`Character.UseStamina`、GC、写盘和结算尖峰做前后对比。

### 最初版本的完整功能边界

最初计划中的核心模型和模块仍作为后续实现参考，不表示当前已经全部完成：

- 数据模型：`RunRecord`、`RunHeader`、`PlayerIdentity`、`PlayerSample`、`InventorySnapshot`、`StatsEvent`、`RunIndexEntry`、`RunStatus`、`RunOutcome`。
- 生命周期：插件启动、Harmony 初始化、RunId 绑定、活动局恢复、正式结束监听、Aborted 标记、后台检查点、完整局合并和最近记录清理。
- 采集器：体力/状态/距离采集器、队友物品栏采集器、物品事件采集器；不修改 `PlayersInfo` 私有代码，不发送新的 Photon RPC。
- 存储器：UTF-8、带版本号的 JSON；临时文件写入后原子替换；活动局每约 5 秒检查点；高频数据串行后台写入；慢盘时允许跳过过时的未封存检查点，但不能跳过已经封存的分块。
- 保留策略：正式结束的 Victory、失败和 Aborted 都进入最近记录；默认保留最近 10 局；收藏数量不设上限且不计入 10 局；活动局不可收藏。
- 调试策略：详细日志由配置控制；常规日志不输出玩家身份、原始上传数据或大段 JSON；错误需要记录阶段、文件和可恢复性。

### 性能优化过程的结论

此前按“8 人、2 小时房间”评估过主要风险，结论是采集对其他客机的网络影响很小，风险集中在本机 CPU、GC、磁盘和结算时刻：

- 玩家对象列表每约 0.5 秒刷新；位置在同一采样帧读取一次；两两距离复用位置结果，避免重复访问 `Center`、字典查找和对象遍历。
- 高频数据使用玩家整数索引、固定状态顺序的 `float[]`、紧凑的距离索引/数值数组，避免每个样本重复写字符串身份。
- 库存从 5Hz 降为 2Hz；先比较值类型指纹，只有内容或资源变化时才生成完整快照和事件。
- 关键拾取、使用、施法完成、消耗和使用次数变化通过即时补丁补充，不能因为库存降频漏掉关键动作。
- 体力曲线维持 5Hz；只对即时 `StaminaChanged` 事件使用可配置阈值，默认绝对变化量 `>= 0.01`，不以降采样替代曲线。
- 序列化、GZip、写盘、局结束结算、整体合并、分析和匿名上传均不能阻塞 Unity/Harmony 主线程；正常退出可以等待后台队列完成。
- 需要记录合并/分析耗时、峰值内存、GC 和失败阶段，才能判断是否需要进一步降低并发或调整分块大小。

### 原计划验收矩阵

后续实现应逐项验证：

1. 新非空 RunId 只创建一份记录；同 RunId 断线重连继续写入；新 RunId 将旧活动局标记为 Aborted。
2. 胜利、正式失败和全员死亡只生成一份正式记录；单人死亡、倒地、复活、传送、力竭不提前结束。
3. 崩溃最多丢失约一个检查点周期的未落盘数据，已封存分块不损坏。
4. 8 人房间中本机距离、两两距离、玩家关联、物品栏、耐久、燃料和使用次数变化均能稳定对应。
5. 碎块合并后样本、库存和事件计数与原始分块一致；时间异常转为质量警告，不静默修正原始数据。
6. JSON 损坏、字段版本变化、单个碎块损坏不会阻止新局记录；失败任务保留原始文件并可重试。
7. 最近 10 局清理不删除收藏；收藏迁移、取消收藏和文件联动保持一致。
8. 未同意匿名提交时无网络请求；网站关闭开关时客户端不能绕过入口；地图上传流程不受影响。

- 合计约 107,130 个样本、6,911 个库存快照、238,915 个事件，数据目录约 36.7 MB；其中约 4 局 Victory、1 局 Aborted。
- `a120f547...` 约 97 分钟，历史上见过 8 个玩家身份，单帧约 4-7 人。
- `635b97e3...` 约 86.5 分钟，历史上见过 11 个玩家身份，单帧约 5-10 人。
- 这两局实际核心采样约 4.8Hz，各有少量时间非递增，但没有旧异常局那样的大幅时间轴重置。
- `77f6bbb7-b690-4b95-9ee1-3b5091aea50d` 曾从约 1719 秒重置到接近 0 秒；分析层必须标记该质量问题，不能直接按时间全局排序掩盖异常。
- 这批样本已经能支持基础概览、时间线、距离关系、物品流水和局间趋势的原型评估，但不足以支撑稳定的玩家评分、最佳队友或战术评级。

### 五局样本驱动的基础分析算法

本节是后续实现依据，不代表分析引擎或面板已经写入源码。当前本机实际复核的五局为 `98fc17ac...`、`77f6bbb7...`、`67eb3a83...`、`a120f547...` 和 `635b97e3...`，合计 `107,130` 个样本、`6,911` 个库存快照、`238,915` 个事件；其中四局 Victory、一局 Aborted。

五局显示，三类数据已经足够支撑第一版：物品栏快照、玩家位置/距离、体力曲线。参考 `LengSword-BetterItemInfoDisplay` 的 Action 和组件分类，用于建立物品语义和字段解释即可，不再把完整 Action 监听作为第一版前置条件。

分析管线固定为：

```text
原始碎块/整体 JSON
  -> 数据质量检查
  -> 双时间轴与有效样本视图
  -> 物品栏差分、体力区段、距离关系
  -> 单局概览 / 玩家时间线 / 物品流水 / 队伍关系
```

#### 1. 数据质量和时间轴

- 原始 `time` 永远保留，不覆盖历史数据。
- 分析层另建 `analysisTime`：遇到时间倒退时切分时间段或单调抬升，并记录 `TimeNonMonotonic` 警告；不能把旧异常局的时间重置静默排序成正常曲线。
- 每个派生指标都带 `quality` 或 `excludedCount`，让面板能说明排除了多少异常样本。
- 位置必须是有限数值，且不接近游戏使用的 `+-5000` 无效坐标哨兵；死亡、观战/离场对象和无效端点不进入有效队伍距离统计，但原始样本仍保留。
- 对存活玩家之间的异常超大距离，不直接删除原始值；派生统计使用有效端点、连续性和稳健分位数，必要时把传送/对象切换标记为 `PositionOutlier`。

#### 2. 物品栏差分

物品分析的主证据是相邻库存快照，即时 Action 事件只作为辅助证据：

- 同一玩家、同一 GUID 的 `uses` 减少，记为高置信度 `UsesDecreased`。
- 同一 GUID 的 `fuel` 减少，记为高置信度 `FuelDecreased`。
- 同一 GUID 的 `cookedAmount` 增加，记为 `CookingProgress`。
- 同一 GUID 的 `useRemaining` 减少，记为 `DurabilityDecreased`，但要和字段语义核对后再显示为耐久。
- 槽位新增、移除、替换、跨槽位移动统一归为 `InventoryFlow`；物品消失不能直接等同于使用，因为还可能是丢弃、转移、死亡掉落或同步延迟。
- 在短窗口内同 GUID 从一个槽位移动到另一个槽位时优先判定为移动；只在没有同 GUID 去向且有 `ItemConsumed`、`UsesDecreased` 或资源变化证据时提高“消耗”置信度。
- 每条推断保存 `Certain`、`Likely` 或 `Ambiguous`，面板显示“资源变化/物品流转”，不要把低置信度结果写成确定的使用次数。

五局中 `ItemRemovedObserved` 为 `3,113` 条，而 `ItemUsesReduced` 为 `390` 条，说明仅按物品消失统计使用会明显夸大消耗；这条规则必须在分析引擎第一版落实。

#### 3. 体力变化区段

- 同时保留 `regularStamina`、`extraStamina` 和派生的总有效体力，不能只看总值而丢失额外体力的消耗/恢复过程。
- 以玩家为单位按 `analysisTime` 计算相邻差值和变化速率；小于噪声阈值的变化不单独展示。
- 同方向且间隔很短的连续变化合并为一个 `StaminaEpisode`，区分消耗、恢复、突发下降和恢复后的稳定段。
- 将区段和同时间窗口内的冲刺、攀爬、滑翔、火箭、倒地、死亡以及物品资源变化关联，输出“发生在什么状态下”，不宣称单一因果。
- 使用前后短窗口关联物品变化，例如食物消失后体力恢复，只作为关联证据；没有直接 Action 或资源字段时显示为推断。

#### 4. 距离和位置

- 每帧两两距离保留原始值；有效统计只使用双方都有有效位置且不处于死亡/离场哨兵状态的 pair。
- 单局和时间线优先使用中位数、P90、最大有效距离、超过阈值的持续时间，而不是简单平均值；五局中死亡端点和异常位置会把平均值明显拉高。
- 第一版输出队伍集合/分散区段、玩家倒地或死亡时最近队友距离、物品变化前后的队友距离，以及玩家移动距离/高度变化。
- 固定阈值只作为展示分桶，建议先使用 `10m / 25m / 50m` 的近中远三档；地图边界和异常传送不能用阈值硬抹掉，必须同时保留质量警告。

#### 5. 第一版不做的内容

- 不做综合玩家评分、最佳队友、战术评级或因果归因。
- 不把 `StateChanged` 的次数直接当作操作能力指标；五局共有 `158,310` 条状态事件，频繁状态切换更适合作为时间线上下文。
- 不为补齐分析而扫描地面物品、增加房间统计 RPC 或监听所有游戏 Action。

## 一局数据的合并方案

### 采集态

采集期间保留当前后台队列和 GZip 碎块设计，逻辑上仍按一局组织：

```text
StateKeeper/
  Runs/
    <run-id>.json                         # manifest、状态、玩家索引、chunk 索引
    <run-id>.chunk-00000.json.gz          # 采集中产生的碎块
    <run-id>.chunk-00001.json.gz
  active-run.json
  index.json
```

### 完成态

后台合并成功、校验通过后，目标结构为：

```text
StateKeeper/
  Runs/
    <run-id>.json                         # manifest 和完整文件索引
    <run-id>.data.json.gz                  # 内部是一个完整 JSON 文档
  Favorites/
    <run-id>.json
    <run-id>.data.json.gz
```

`*.data.json.gz` 仍然是压缩文件，但解压后是一份完整的单局 JSON，不在分析时要求 UI 逐个读取碎块。manifest 保留版本、局状态、合并状态、数据质量警告、字节数和样本/库存/事件计数。

合并失败或取消时必须保留所有原始碎块，不能删除可恢复数据；只有“完整文件写入、重新打开解压、schema/计数校验均通过”后，才删除已合并碎块。合并、压缩、校验和清理均放后台线程，不在 Unity 主线程执行。

### 合并任务与进度

合并任务独立于分析任务，阶段预留：

```text
Queued -> Reading -> Merging -> Compressing -> Verifying
       -> CleaningChunks -> Completed
```

进度使用 chunk 数、当前字节数和阶段权重计算，面板至少显示：当前局、当前 chunk/总 chunk、阶段和百分比。异常显示 `Failed`，用户可以重试；大型文件不使用一次性字符串拼接，优先采用流式/分段序列化策略。

## 分析任务与进度

具体评分、最佳队友、战术评级和复杂算法暂时不考虑，但先建立真实任务接口和取消机制，避免以后把分析工作塞进 UI 主线程。

预留阶段：

```text
LoadingManifest -> ReadingSamples -> ReadingEvents -> ReadingInventory
                -> BuildingTimeline -> BuildingPlayerSummary
                -> BuildingTeamSummary -> BuildingItemSummary -> Completed
```

分析使用独立的 `AnalysisProgress`、取消令牌和错误状态；不能复用合并进度百分比。第一版可以只完成加载、数据质量检查和基础摘要，但 UI 必须如实显示“准备数据/暂未实现具体分析”，不能用假进度掩盖等待。

## 面板与本地化

- UI 参考 `WhereIsThing` 的原生 PEAK UI、布局、按钮交互和字体兜底；不修改 `WhereIsThing`。
- ESC 暂停菜单入口参考 `LengSword-ClimbInfoTracker` 的 `PauseMenuMainPage.Start`、`UIPage`、`IHaveParentPage`、`UIPageHandler` 和原版按钮模板，放在用户截图红框对应的安全位置。
- 页面入口显示 `STATE KEEPER` / `状态分析`，具体语言跟随游戏语言。
- 远征列表分为最近记录和收藏记录；每行显示日期/时长、结果、玩家数、数据状态、合并状态和收藏按钮。
- 收藏/取消收藏放入列表行和单局详情页；活动局不可收藏，收藏局不参与最近 10 局清理。
- 移除 `FavoriteHotkey` 配置和 F8 处理，不保留快捷键兼容行为。
- MODCONFIG 的名称、说明、枚举和值文本，以及面板的按钮、进度、错误和隐私确认均准备中英文资源。

## 自愿匿名提交与 PEAK-MAP

网站源码：`C:/Users/Administrator/Desktop/MOD/PEAK-MAP`。

StateKeeper 不直接复用网站现有地图上传 API。网站后续新增独立接口和独立数据表，例如：

```text
app/api/statekeeper/submit/route.ts
statekeeper_submissions
statekeeper-submissions/<random-id>.json.gz
```

推荐流程：

```text
面板选择一局
  -> 本地脱敏
  -> 展示脱敏摘要和隐私说明
  -> 用户明确勾选自愿提交
  -> 独立 API 上传
  -> 服务端再次校验/脱敏
  -> 私有 Cloudflare R2 保存
  -> Supabase 只保存元数据、状态和统计摘要
```

匿名策略采用“玩家可理解的适度脱敏”：界面上把玩家名称显示为本次提交内的“玩家 A/B/C”等匿名编号，每次提交重新随机分配；技术层仍删除可追踪标识。具体规则为：删除 Photon UserId、ActorNumber、物品 GUID、精确 UTC 时间、原始 `detail`、本地路径、机器名、配置路径和日志内容；`runId` 替换为一次性随机提交 ID；局内时间保留相对秒数；距离四舍五入到约 5-10 米；绝对位置默认删除或粗粒度化；事件只保留白名单字段，数值字段先提取再上传。远端观察事件仍保留来源标记，不能伪装成本地权威事件。

玩家确认文案应明确说明：玩家名称会显示为匿名编号，不上传账号 ID、物品 GUID、精确坐标、机器信息或日志；数据可能用于改进 STATE KEEPER。默认不提供“上传原始详细数据”选项；如果未来确实需要更高精度，应单独征得同意，并继续使用私有存储和独立保留策略。

提交前必须让用户看到匿名化摘要并明确同意，说明用途、是否保留和删除方式。最好给每次提交生成一次性删除令牌；匿名提交不能依赖登录用户身份完成删除。站点应提供环境变量或 `site_config` 关闭入口，未来数据足够或功能完善后可以关闭该功能。

R2 原始匿名文件默认私有，不直接接入公开文件代理；Supabase 保存 `pending/reviewed/rejected/approved` 和计数摘要。服务端增加独立限流、文件大小限制、GZip/JSON/schema 校验、解压后大小限制、深度/数组/字符串上限、失败清理和不含原始数据的安全日志。

## 性能边界

- 采集仍按当前优化后的 5Hz 核心采样、2Hz 库存和阈值事件记录运行；不为面板牺牲采样质量。
- 合并和分析采用后台任务、分阶段读取、流式处理和有界队列；UI 只接收轻量进度快照。
- 面板打开时只读取 manifest/index；用户进入详情时再加载对应完整文件，避免启动或打开菜单时读入全部历史局。
- 多局分析按局逐个加载并释放，不能把所有局的完整 JSON 同时放入内存。
- 上传优先使用已经合并的整体 GZip，不在上传前重复构建大字符串；上传前只生成匿名副本或匿名流。
- 记录合并耗时、分析耗时、峰值内存、失败阶段和上传大小，但不把玩家身份写入诊断日志。

## 实施顺序

1. 先实现数据 manifest/合并任务/校验/失败保留和合并进度条。
2. 再实现详情按需加载、分析任务接口、分析进度条和数据质量提示。
3. 接入原生暂停菜单入口、双语面板和面板内收藏，删除 F8 配置/代码。
4. 在 PEAK-MAP 新增独立 StateKeeper 提交 API、R2 私有存储、Supabase 元数据和可关闭开关。
5. 加入本地/服务端双重脱敏、用户确认、删除令牌/管理员删除流程和限流安全校验。
6. 先用本地真实数据验证合并、基础分析、面板和匿名导出，再进行网站端到端测试；复杂评分类算法另立计划。

## 验收标准

- 一局最终可以从多个碎块生成一份可独立解压、校验和读取的整体 JSON；失败不丢碎块。
- 合并与分析同时存在时，两个进度条相互独立且都能取消/报错。
- 面板从 ESC 菜单进入，语言切换后入口、按钮、配置和状态文本完整切换。
- 收藏只通过面板完成，收藏局不被最近 10 局清理。
- 未勾选同意时不产生网络请求；关闭提交开关后客户端入口不可用。
- 上传包中不存在玩家身份、精确时间、GUID、原始路径、原始 detail 或可直接定位玩家的坐标。
- 网站地图上传流程不受影响，StateKeeper 数据不写入 `maps` 表，不使用公开 R2 代理。
- 8 人、2 小时长局下，合并和分析不阻塞游戏主线程，内存峰值和 I/O 可从日志核对。
