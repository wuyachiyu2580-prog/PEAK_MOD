# 互喂与救援：可见范围、已有证据和实现边界

日期：2026-09-08。此文接续 `RESEARCH_2026-09-08.md`，包含本轮实际代码修改；不得把早先“仅调研”的状态当成本轮状态。

## 1. 不是只有主机被喂才有线索

PEAK 2.4.b 源码路径均在 `引用参考代码/反编译/2.4.b/Assembly-CSharp/`。

| 路径 | 能观察到什么 | 不能声称什么 |
| --- | --- | --- |
| `Character.FeedItem` / `GetFedItemRPC`，Character.cs:1638 | 请求发给被喂角色 Owner；执行时临时设置 overrideHolderCharacter | 主机没有旁观所有互喂的特权，本机也不必是主机 |
| `Item.ConsumeDelayed` / `Consume`，Item.cs:1095 | 隔一帧向全员广播 consumerID；消耗前能保存 GUID、消费者和真实持有者 | 不是所有工具/持续治疗都走 Consume；消耗不等于有效治疗 |
| `Item.TryGetFeeder`，Item.cs:1413 | trueHolderCharacter 与有效 holderCharacter 不同可确定馈赠方 | 旧局仅有库存主人时仍是推断，不能填成直接 actor |
| `Action_ModifyStatus.RunAction` | 本机被治疗时可在前后读取状态；可知道馈赠方 | 第三方之间的全部治疗、全队总治疗量 |
| `RescueHook.RPCA_RescueCharacter` | RpcTarget.All：可以观察远端发起者命中目标、启动拉回 | 命中不代表避免死亡，更不是复活 |
| `Character.RPCA_ReviveAtPosition` | 可以确认角色复活/被拉起的结果 | 参数没有施救者；不把广播主机当作救援者 |
| `GameUtils.RPC_ThrowOrIncrementGenericAchievement` | 急救/治伤/解毒奖励定向发给施助者客户端 | 不是全员广播，参数没有完整物品和目标关系，不作全队计数来源 |

`RespawnChest.Interact_CastFinished` 带 interactor，但开箱/生成/复活会跨客户端执行，远端复活 RPC 无该身份；箱子也能被 Break 或其他系统打开。`ScoutEffigy.FinishConstruction` 可在施放端看到持有人，但复活 RPC 只有目标/位置/状态标记。未来可研究请求与结果关联，本轮不把主机或最近玩家归为救援者。

## 3. 记功口径与新增低频事件

本轮实际添加/修正：

- `PlayerFriendHealed`：仅明确 actor != target，读取实际前后状态差。锁定状态、未改变、非有限数、自疗均不记。resourceKey 标明被减少的状态；value是该次观察到的减少量，不是全队治疗总量或标称道具量。
- `PlayerLifeSaved`：更准确的显示名称是“急救越过昏迷阈值”。原来已昏迷，负面状态和从 >0.99 降至 <=0.99，目标未死且石化<100。阈值取自 shouldPassOut；它不是原成就分支的<=1，也不是已完成复活。连续多个治疗 Action 只有越过阈值的一次计入。
- `PlayerRescuePulled`：观察到救援爪启动拉回。保留 actor/target；移除仅 actor.IsLocal 才收集的限制。与急救计数分开。
- `PlayerRevivedObserved`：从死亡/倒地到复活的现有RPC结果，只保存目标，不给未知救援者记功。
- 在已有 collectionCapabilities 中标记 `LocalRecipientTreatment`、`BroadcastRescuePull`、`ReviveTargetOnly`。旧局未采集显示未知；新局也注明观察覆盖不完整，不能用不对称覆盖做全队救人排名。

这些是低频事件和采集能力标记，不添加网络RPC，不提高5Hz/2Hz频率，不扫描地面物品。普通/额外体力/普通状态原已采集；精确石化仍使用前轮新增的 nullable petrifyAmount。不必为了这轮救援调研再加一组5Hz字段。

注意：Action_ModifyStatus只覆盖对应的直接状态修改，持续治疗、范围治疗、MOD自定义作用和清除Affliction不等于全部已覆盖。统计名不可简写为全队完整“治疗量”。

## 4. 没有直接事件时的算法

按证据由强到弱，不给事件消失强行找原因：

1. 消耗消费者ID + 同GUID持有历史，建立物品/来源候选/目标关系。明确actor与库存推断actor分开存。
2. 核对目标的伤、毒、困倦、其他状态、额外体力、Affliction等结果通道，而不是只看绿色体力。即时效果允许消耗事件之前的小幅偏移；蘑菇等按已知机制时延处理。
3. 若只有资源减少或库存消失：先建立弱候选，再核对同一连续观察区间中的机制匹配变化、存活、位置、身份和同期其他候选。单纯消失保持不明确；转交、丢弃、死亡掉落不记为使用。
4. “可能帮助”必须与“观察到恢复”分开。自然衰减、营地恢复、其他治疗、复活、时间断裂是竞争解释。存在多候选或缺关键证据不做唯一归因。
5. “可能救人”至少还需要先前昏迷与后续恢复，并排除系统复活等；只减少Injury不能算救人。没有可靠来源时仍能展示某玩家恢复，但不给其他人记功。

**实现状态**：已有引擎支持消费事件、GUID候选和部分状态结果关联；资源减少/纯库存候选的完整跨玩家匹配、机制时延/范围/持续效果规则、竞争环境解释仍未完整实现。本轮没有声称旧局已能精确排列救人榜，也没有把5条候选硬转为救援计数。
